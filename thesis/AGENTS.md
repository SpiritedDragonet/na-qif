# Project Agent Rules

## Iteration Policy

- 当前项目以快速迭代和方案验证为主，重点是尽快收敛到更清晰的主路径，而不是长期维护多套实现。
- 因此在引入新路径或新方法后，默认做法是及时清理旧路径及相关冗余逻辑，避免双路径并存带来的复杂度和维护成本。
- 若确有必要保留旧逻辑（例如直接关系到关键对照、复现实验结果或短期评估），应在变更说明中写清原因，再决定是否保留。

## Execution Preference

- 禁止新增脚本文件（如 `scripts/*.py`）来完成一次性排查或标定任务。
- 优先直接使用 `python -c "..."` 执行临时计算、扫描与验证。
- 仅当用户明确要求时，才允许新增可复用脚本。

## Writing Style

在撰写报告、文档、技术解释、分析或任何长篇内容时，应使用清晰、流畅的散文，采用完整的段落和句子。通过标准的段落换行来组织结构，并将 markdown 主要用于 `inline code`、代码块（```...```）以及简单标题（如 `###`）。避免使用加粗或斜体格式。

除非满足以下情况，否则不要使用有序列表或无序列表。其一，所表达的内容确实是彼此独立的项目，且列表形式最为合适；其二，用户明确要求使用列表或排名形式。

不要用项目符号或编号来罗列内容，而应将各个要点自然地融入句子之中。这一原则在技术写作中尤为重要。采用连贯的散文表达而非过度格式化，可以显著提升阅读体验。应避免输出一连串过于简短的要点式条目。

目标是生成具有良好可读性的连贯文本，使读者能够顺畅地理解内容的发展脉络，而不是将信息割裂为彼此孤立的片段。

此外，每句话必须可以独立成立，不依赖对另一个观点的否定。写作示例如下。

```text
这样坏：我不会单纯写一段高耦合的代码，而是写成一个函数再引入。
这样好：我将写一个函数并引入。
这样坏：真正的创新者不是"有创意的人"，而是五种特质同时拉满的人。
这样好：真正的创新者是五种特质同时拉满的人。
这样坏：这更像创始人筛选框架，不是交易信号。
这样好：这是一个创始人筛选框架。
```
